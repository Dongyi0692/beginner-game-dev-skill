# 策划前多维度问答表 v1.2（通用母版）

版本：v1.2｜日期：2026-11-10｜基于《游戏开发全流程通用规范》v1.2 整理

本表用于以后启动新项目时收集需求，**不是要求现在填写某个新项目的调查表**。每个新项目开始写策划案之前，先以本表为基础生成一份针对该项目的完整问答表；已经明确的信息直接注明来源和现有答案，缺少或矛盾之处再请用户补充。已有项目新增或改动功能时，使用末尾的简短确认单，只追问受影响的需求，不重填整套108题。

## 使用与填写规则

- **启动必答**：会影响项目方向、范围、成本、视觉或验收的关键信息。允许回答“请先给我方案”，但不能把未选定的方案写成已确认要求。
- **可后置**：不影响当前阶段的细节，可标记“待定”，记录最迟决定阶段。
- **条件适用**：仅在相应功能、平台或生产方式启用时填写；不适用时直接注明。
- 用户可以自然、口语化地回答，AI负责整理“目标＋背景＋要求＋限制＋验收”。先说明想获得的体验或结果，再讨论实现方式；用户不必为显得专业而指定自己不理解的技术方案。
- 每项答案均可使用“明确答案／待比较方案／请 AI 建议／不适用”。选项只是帮助表达，不限制自由回答；不知道如何回答时，AI先给少量不同方向与取舍，不能自行决定后记为用户要求。
- 每题的答栏按“答案：……；来源：……；确认状态：……”分别记录。来源区分“用户明确要求／上下文推断／AI额外建议”，并注明原话或资料；确认状态使用“已确认／待确认／已取消／不适用”。推断不是事实，建议不是授权；用户已明确表达当前具体要求可记为已确认，无需再走一次形式确认。
- 首次提供完整问答表，允许按主题分批回答；先处理启动必答项，不要求一次答完全部问题。
- 正式策划前，将答案归纳为“已确认需求、仍待决定的问题、建议方案及其影响”。关键缺项或冲突需解决；低影响细节可带明确的待定标记进入下一阶段。
- 只有用户明确授权时，才可按注明的假设先写策划草案；草案中的假设不得表述为已确认要求。
- 不相关的章节标为不适用；若题材或技术有特殊要求，在对应维度增补问题。每个必答项都必须有有效答案、明确授权的暂定方案，或说明为何不适用。
- 下面的空白答栏在实际新项目中填写。回答改变后，同步更新策划、任务范围与验收标准。

## 本次任务意图与执行边界

AI应从用户表述判断当前要做的工作，不要求用户先选专业标签；只有任务意图会影响是否修改成果且仍不清楚时才询问。

| 任务意图 | 本次产出与边界 |
|---|---|
| 探索 | 分析问题、比较方向与取舍，不把候选方案直接实施。 |
| 需求整理 | 复述原意，整理明确要求、推断、建议和歧义，不擅自增加功能。 |
| 执行 | 在已确认或明确授权的具体范围内实现，重要歧义先解决。 |
| 审查 | 判断当前成果是否有实质问题，区分必须修复、值得改进、可选建议和保持原样；不默认修改。 |

从探索、整理或审查转为实施，需要用户授权；用户已明确要求在具体范围内实施的，沿用该授权。新增或改动功能、改变玩家体验或视觉方向、扩大范围或费用、修改已验收内容等重要节点，先用末尾确认单说明变化与影响。尚未明确的关键决定须等待答复，未受影响且已授权的工作可以继续。确认仅覆盖写明的范围，不能据此扩展为其他功能的授权。

需求明确仍应留意它对项目的影响：小型、可逆且已授权的任务直接执行，不要求六维报告；涉及多个系统、长期方向或重大成本时，简要说明目标一致性、玩家价值、开发成本、系统影响、维护和机会成本。学习、艺术与探索也可以是明确目标，不以最省成本作为唯一尺度。发现足以改变选择的实际问题，应提出依据和适用替代；证据不足时建议有预算/时间上限、观察标准与退出办法的可逆小试验。用户了解同一取舍后决定的，不反复劝阻或擅自换方案；只有实质新风险或授权范围变化才重新确认相应部分。具体执行原则见本 Skill 的 SKILL.md。

## 新增或改动功能前的简短确认单

此表用于具体功能或重要变更，**不替代新项目策划前的完整问答**。AI先根据已有信息填好，只请用户补充关键缺口或选择；可在一条消息中完成，不要求另建文档。简单且明确的已授权任务可以压缩表达，但仍应保留必要的范围与验收依据。

| 字段 | 本次需要说明的内容 |
|---|---|
| 1．目标与背景 | 现在有什么问题，为什么要改，希望玩家或用户得到什么结果。 |
| 2．变化前后 | 现有行为是什么，拟新增、修改或删除什么；区分明确要求与候选方案。 |
| 3．范围与优先级 | 本次必须做、可选和不做的内容。 |
| 4．保持不变与禁区 | 哪些操作体验、数据、画风、文件或已验收成果不能动；允许自由决定哪些实现细节。 |
| 5．交付 | 这次交付方案、样例、代码、可运行功能还是其他成果。 |
| 6．验收 | 在什么条件下进行哪些操作，应得到什么结果；需要什么证据。 |
| 7．影响与代价 | 按影响深度说明目标/玩家价值、开发成本、系统影响、维护及机会成本；给出适用替代，区分事实、判断、偏好与假设；小改动简述即可。 |
| 8．授权与未决事项 | 已确认范围和已接受取舍及依据；仍需决定的关键问题；如需试验，记录上限、观察标准、停止与扩大边界；此次确认不包含哪些后续改动。 |

确认后再开展依赖该决定的实现。用户已经明确授权同一具体范围时，复述并记录即可，不重复等待；关键歧义没有回答时，不以沉默作为批准。发现范围或前提变化后，只重新确认变化部分。每次生成操作脚本前是否运行验证，仍按 Q101 单独明确，不能由这张确认单的一般实施授权代替。

建议不等于用户决定。AI可依据项目目标提出反对意见，但用户知情选择后仍应按其决定执行，不以相同理由反复阻拦；复用本表记录重要取舍，不另加一轮影响审批。AI不能因为推荐试验就自动开展或扩大试验。
